# midbrain-memory-mcp v0.4.8

## TLDR

v0.4.8 restores NanoClaw episodic capture that v0.4.7's hook migration
silently broke, hardens credential handling end to end, unifies API-host
resolution between the MCP server and capture hooks, and adds an account
keystore plus a `memory_diagnostics` tool.

- Containerized (NanoClaw) capture self-heals: the MCP server persists its
  environment API key to the global key file at startup so hook children can
  authenticate without environment passthrough.
- Broken installs recover on the first fresh container after updating — no
  user action required.
- Credential writes now go through one guarded atomic writer, and the
  installer can no longer promote credentials across scopes.
- The MCP server and capture hooks resolve the API host identically, so
  self-hosted configurations cannot split across origins.
- A new account keystore stores multiple account credentials; a new
  `memory_diagnostics` tool explains authentication and capture failures.
- NanoClaw captures can carry an accurate `nanoclaw` client label via an
  opt-in marker written by the NanoClaw skill.
- Breaking changes: None.

## Overview

This release combines the complete unreleased delta since v0.4.7: the
credential-safety and diagnostics series (PRs #42–#45), the account
keystore (PR #37), and the NanoClaw capture-restoration pair (PRs #47 and
#49, closing issues #46 and #48).

The headline is an incident repair. v0.4.7's hook migration moved Claude Code
capture to a stable shim and, in doing so, discarded the inline
`MIDBRAIN_API_KEY=` prefix that containerized NanoClaw installs depended on.
In that topology no key remained on any path a hook child could resolve, so
episodic capture failed silently — hooks logged `NO KEY` to a
container-ephemeral file and exited 0. Every standard NanoClaw + MidBrain
install running `@latest` was affected from 2026-07-27 until this release.

## NanoClaw Capture Restoration (issue #46)

The durable fix ships in the package, so already-broken installs heal
themselves:

- At MCP server start, self-repair persists the server's environment
  `MIDBRAIN_API_KEY` to the global key file (`~/.config/midbrain/.midbrain-key`)
  through the central guarded writer: absence-only, atomic, `0600`, never
  replacing or backing up an existing credential.
- Hook children then authenticate through the standard key-file resolution
  chain — no environment passthrough required, which containerized setups
  never provided.
- The write is guarded: it is skipped when `MIDBRAIN_API_URL` is set (a
  self-hosted key is never stranded on the default origin for env-less
  hooks) and skipped unless the server's own resolution selected the
  environment key (no promotion over an active project, client, or global
  file credential). It runs after hook repair and is fully error-contained.
- Hook migration remains a sanitizer: environment prefixes on MidBrain-owned
  hook commands are scrubbed on rewrite; the persisted key file is the single
  credential-delivery path.
- Because both the NanoClaw MCP command and the stable shim run
  `midbrain-memory-mcp@latest`, the first container created after this release
  picks up the fix, persists the key, and capture resumes — validated live on
  a production NanoClaw group before release.

## Credential Handling Hardening

- Every credential write goes through one central guarded writer: atomic
  temp-file publish, `0600`/`0700` modes, symlink-safe, refusing to replace a
  different existing key (PR #44).
- The installer can no longer promote credentials across scopes; scope
  selection is explicit and conservative (PR #44).
- A new account-management keystore stores multiple account credentials and
  supports switching between them. The keystore is deliberately never
  consulted by capture-hook credential resolution, which keeps capture
  behavior stable and predictable (PR #37).

## Unified API-Host Resolution

The MCP server and the capture runtime previously resolved the API host
through slightly different paths, which could split a self-hosted
configuration across origins. Both now resolve identically (PR #43).

## Authentication and Capture Diagnostics

A new `memory_diagnostics` MCP tool reports credential-resolution state,
capture-hook health, and actionable failure explanations, turning previously
silent authentication and capture failures into visible, diagnosable ones
(PR #45).

## Capture Client Labeling (issue #48)

Captures from NanoClaw containers were labeled `claude` on the dashboard,
because inside the container the runtime genuinely is Claude Code. Capture
hooks now resolve the client label as: `MIDBRAIN_CAPTURE_CLIENT` environment
variable → first line of `~/.claude/.midbrain-capture-client` (validated
against `^[a-z][a-z0-9-]{0,31}$`) → `claude`. The NanoClaw skill writes the
`nanoclaw` marker into the group's mounted settings directory at install
time. The resolution is fail-open: any missing, unreadable, or invalid
marker falls back to the previous behavior, and the label is never logged
(PR #49).

## Compatibility and Operational Notes

- No MCP tools were removed or renamed; `memory_diagnostics` is additive.
- Hosts with an existing global key file are strict no-ops for the new
  startup persistence. One disclosed behavior change: when the server
  environment carries `MIDBRAIN_API_KEY`, no `MIDBRAIN_API_URL` is set, no
  file credential is active for that server, and no global key file exists,
  one is created (absence-only).
- Key rotation on containerized installs: a persisted key file outranks a
  rotated environment key until the container is recreated (a fresh
  filesystem re-persists the current key) or the file is removed on durable
  hosts.
- Existing NanoClaw installs keep the `claude` capture label until their next
  skill run writes the capture-client marker; capture itself heals without
  any action.
- The very first hook of a freshly created container can race startup
  persistence and miss once; subsequent captures proceed normally
  (persistence is re-attempted at every server start).

  test, task, or credential files).
