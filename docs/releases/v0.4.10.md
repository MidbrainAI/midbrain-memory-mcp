# midbrain-memory-mcp v0.4.10

## TLDR

v0.4.10 closes the final untouched-legacy NanoClaw cold-start gap and makes
`grep` and `read_file` behavior more predictable across current backend result
shapes.

- Recovers the opening user message for the exact untouched NanoClaw legacy
  cold-start failure while leaving migrated NanoClaw and plain Claude behavior
  unchanged.
- Makes `grep` retain semantic and episodic lexical matches by default, adds an
  optional memory-type filter, and formats mixed result shapes consistently.
- Makes `read_file` return its friendly missing-file response without retrying
  the GET-only semantic-file endpoint with POST.
- Keeps legacy-opener recovery narrow and terminal: one transcript-attested
  POST attempt, with no recovered-user spool, cache, or retry.
- Breaking changes: none.

## Overview

This release contains the complete delta since v0.4.9: PR #81 fixes semantic
file 404 handling, PR #82 makes lexical `grep` additive across semantic and
episodic result shapes, and PR #83 closes issue #71 for untouched NanoClaw
groups that still carry the historical v0.4.8 Claude hook topology.

The NanoClaw change does not broaden recovery into a general replay system.
It activates only when the current Stop transcript proves one exact owned
legacy `UserPromptSubmit` exit-127 failure in the current assistant's ancestry.

## Final Legacy NanoClaw Cold-Opener Recovery

An untouched NanoClaw group can start a fresh container with hook settings
written by v0.4.8. In the affected ordering, Claude processes the opening user
message before MCP startup repairs the historical shim. The old
`UserPromptSubmit` command fails to launch, self-repair completes afterward,
and the assistant Stop hook runs normally—but the opening user row was never
captured.

v0.4.10 lets that Stop hook recover the opener only when all of the following
are true:

- the capture client is `nanoclaw`;
- the guarded transcript is a regular file contained under Claude's projects
  root and only its final 4 MiB are read;
- the transcript contains exactly one owned historical v0.4.8 user-shim
  exit-127 failure in the current assistant's valid UUID ancestry;
- the terminal assistant matches the Stop event's session, working directory,
  and rendered assistant text;
- the fixed recovery receipt does not already exist.

The sole receipt creator makes one recovered-user POST attempt before the
normal assistant capture. The recovered row never enters the spool or offline
cache, and every recovery error leaves assistant capture intact. Repeated Stop
events, already-migrated groups, foreign hooks, direct v0.4.7 commands, invalid
ancestry, untrusted transcripts, and ordinary Claude Code hosts do not qualify.

The receipt is a terminal at-most-once attempt boundary. A crash after receipt
creation but before the POST completes can still lose the opener; crash-atomic
exactly-once delivery would require server-side idempotency.

## Additive Lexical Search Results

The `grep` MCP tool now supports `memory_type=all|semantic|episodic` and
forwards the selected filter to lexical search. The default remains `all`, but
it now preserves semantic and episodic results in the API's original order
instead of assuming every row has the legacy semantic shape.

Mixed rows receive intentional location or type labels rather than rendering
JavaScript `undefined`. Existing semantic output remains compatible. When a
`source` constraint is supplied with `memory_type=all`, matching source-less
episodic rows may still appear because the source filter applies to semantic
files.

## Friendly Missing-File Reads

`read_file` now disables the legacy GET-to-POST compatibility fallback for the
GET-only semantic-file endpoint. A real 404 is preserved and converted into
the existing friendly not-found response after exactly one GET. Other API
callers retain their existing fallback behavior.

## Compatibility and Operational Notes

- No MCP tools, bins, configuration formats, dependencies, or credential
  locations were removed or renamed.
- Existing `grep` callers keep additive `all` behavior by default.
- Already-migrated and newly configured NanoClaw groups continue through the
  normal user and assistant hooks without legacy recovery.
- Plain Claude Code remains labeled `claude` and is ineligible for the
  NanoClaw-only fallback.
- Package and lockfile versions advance together to 0.4.10.

## Testing

Release verification includes:

- the canonical build, lint, 1,237-test Vitest suite, pinned-spec checks, and
  copied-topology credential-isolation suite;
- focused MCP compatibility coverage for missing-file 404s, mixed lexical
  result shapes, default/additive ordering, and memory-type filtering;
- guarded transcript, ancestry, receipt exclusivity, fail-open, spool/cache,
  NanoClaw topology, and cross-platform Claude hook coverage;
- package-content, version, dependency/lock-drift, secret, and forbidden-file
  inspection;
- real WhatsApp NanoClaw validation in which one legacy cold turn produced the
  real owned exit-127 failure, one recovered opener, and one completed
  assistant capture, followed by a second true-cold normal turn with no
  recovery reuse or duplicate/spool/cache amplification;
- exact restoration of the prior NanoClaw image, hooks, durable state, marker,
  session state, and router, without changing credential contents.

The legacy live ordering used a test-image-only MCP startup gate that waited
for the real token-bound exit-127 transcript attachment. It did not inject a
message, edit a transcript, invoke capture directly, warm up, or retry. A
separate brand-new NanoClaw-group live readback was not rerun; new-group and
negative paths remain covered by the automated matrix.
